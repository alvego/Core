# Кейс: сервер-лок при мультипрессе ротации энх шамана — план диагностики

Статус: **план утверждён, реализация не начата** (база — коммит `efda9e9`).
Документ — точка входа для сессий по этой теме. Меняем по ходу дела.

## 1. Наблюдение (субъективное, не подтверждено измерениями)

Владелец: ротация периодически «прожимает несколько спеллов одновременно»,
сервер отвечает локом (задержкой), вся ротация сдвигается. Встроенная
телеметрия однозначного ответа не даёт. Решено: сначала измерительный
инструмент, диагноз потом. Ничего в поведении ротации не чиним до замера.

## 2. Рабочая гипотеза (анализ от 2026-10-18)

Механика тика (`Lib/Events.lua: onUpdate`): в хвосте GCD, пока
`gcdLeft ∈ (0, c.advance]` (0.05с), `immediatelyTimer` перезапускается каждый
кадр → ротация выполняется **каждый кадр**, а не раз в `updateDelay` (0.25с).

Клиентский GCD стартует только по подтверждению сервера. Между `bUseAction`
и ack (~RTT) клиент считает GCD свободным: `st.gcd = false`, слотный кд = 0.
Гварда «нажал — жду подтверждения» нет (`st.lastAction` пишется
в `Lib/Actions.lua: DoAction`, нигде не читается).

Итог: до ack ротация каждый кадр жмёт тот же спелл повторно
(при RTT 100мс и 60fps ≈ 6 лишних прессов на хвост GCD). Сервер отбивает
повторы «Еще не готово», а это сообщение лежит в `skipErrors`
(`Lib/SpellError.lua: onErrorUpdate`) → `FAILED:`-таймер не ставится →
повтор ничем не блокируется. Гипотеза: серия кастов внутри серверного GCD
триггерит сервер-лок Сируса.

Вторичные источники мультипресса (реже):
- коллизия ручной очереди `userAction` (`Lib/ActionHooks.lua: updateUserAction`)
  с ротацией в одном кадре — не координированы;
- смена ветки ротации внутри RTT-окна до ack.

Преимущества ротации, которые НЕЛЬЗЯ потерять при будущем фиксе:
- преднажим в хвост GCD (порог `c.latency` в `c.IsReadySpell`,
  `Lib/Spells.lua`) — пакет ложится точно на конец серверного GCD;
- быстрый retry в busy-окне после реального отказа.

## 3. Цель

Инструмент «чёрный ящик»: полная машинная запись press/ack/error/decision
+ офлайн-разбор. Критерии успеха — метрики из §6. Только после этого —
решение по фиксу (кандидат: in-flight guard в единой точке `bUseAction`,
сброс по `UNIT_SPELLCAST_SUCCEEDED/FAILED` или таймауту `max(RTT*1.5, 0.15s)`).

## 5. Архитектура Recorder

Новый `Lib/Recorder.lua` (~200 строк) + строка в `DrDamage.toc`.
Всё время — `GetTime()` (CLEU-таймстемп дублируем в запись для сверки).
Запись позиционными массивами `{t, kind, spell, ...}` — компактно.

Каналы:

| Канал | Источник | Содержимое |
|---|---|---|
| P press | единая точка `c.bUseAction` (закрывает `DoAction`, `DoSpell`, `updateUserAction`, ручную очередь) | спелл, слот, source (rotation/user/manual), reason, `st.gcd`, `gcdLeft`, `c.latency`, FPS, Lag |
| A ack | доп. подписки `UNIT_SPELLCAST_SUCCEEDED/START/FAILED/INTERRUPTED` + CLEU `SPELL_CAST_SUCCESS/FAILED` | press→ack = реальный RTT |
| E error | доп. подписка `UI_ERROR_MESSAGE` — ВСЕ тексты, включая skip-лист | маркер мультипресса и сервер-лока |
| R decision | `updateEnhance/updateElemental` — только смена reason | «жали X, приземлился Y» |

Урон/бафы/дебафы НЕ пишем (опционально — только свои `Удар бури` /
`Огненный шок`, если понадобится анализ ветки «вскипание перезжим»).

Правила безопасности замера: нулевой чат-вывод в бою, лёгкие подписки,
буфер без аллокаций на тик; во время замера поведение аддона не меняем.

## 6. Метрики и критерии

1. **Burst** — P-событий одного спелла до первого ack. Гипотеза: 2–8; норма после фикса: 1.
2. **Доля reject'ов** «Еще не готово»/«Заклинание пока недоступно» на каст.
3. **press→ack** медиана/перцентили vs `c.latency` — адекватность порога `advance`.
4. **Пауза после reject-серии** — рост интервала до следующего `SUCCEEDED`
   после burst'а reject'ов против обычного хвоста GCD. Отличает
   «сервер карает» от «сервер просто отбивает».
5. Кросс-чек с HUD-телеметрией (Lag/FPS зашиты в P-события).

Подтверждён мультипресс: метрика 1 > 1 и метрика 2 существенна.
Подтверждён сервер-лок: метрика 4.

## 7. Тест-протокол (маникен)

1. Включить запись (слэш/кнопка), бой с маникеном 3–5 мин, автоатака+ротация.
2. Дубль 2 — с искусственно завышенным `c.latency` (флагом): поведение
   хвостовых прессов при плохой сети.
3. Стоп → дамп в `CoreDB` → офлайн-скрипт → сводка по метрикам §6.

## 8. План работ

1. `Lib/Recorder.lua`: буфер, подписки (НЕ трогая `SpellError`), старт/стоп +
   слэш, дамп в `CoreDB`, строка в `.toc`.
2. Инструментация: `c.RecordPress(...)` внутри `bUseAction`
   (+ опц. `updateUserAction`) — 2–4 строки в существующих файлах.
3. Телеметрия: 2 счётчика (max burst, reject/min).
4. Офлайн-скрипт вне аддона (Python): парс `CoreDB.lua` → таймлайн/сводка.
5. Только по результатам: решение о фиксе (in-flight guard), отдельный кейс.
